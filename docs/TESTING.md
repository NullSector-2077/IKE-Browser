# Automatic tests

`tests/` holds checks that start the real browser without a display (PyQt6 +
Qt WebEngine, `QT_QPA_PLATFORM=offscreen`), each time with an empty profile in
a temporary folder and without downloading anything, and look at it from the
inside. From the repository root:

```bash
python3 -m pytest
```

Needs `python-pytest` besides the dependencies of the PKGBUILD; the desktop
integration tests also need `dbus-daemon` and `gdbus` (skipped without them),
and the screen test `ffmpeg`. Every other test runs without a session bus. The AdBlock
engine tests need the engine built into `vendor/adblock/` (see BUILDING.md);
without it they are skipped. The whole run takes a few minutes.
To test an installed copy instead of the repository:
`IKE_TEST_APP=/usr/lib/ike-browser python3 -m pytest`.
The Rust module has its own small test
(`cargo test --no-default-features --locked --manifest-path ike-adblock/Cargo.toml`).
A test fails when the browser logged an internal error during it, even if
everything it looked at was right (`internal_errors=True` for the tests that
cause one on purpose).
`python3 tests/measure_startup.py` gives the median start-up time, to the
first window and to the first page (the same variable chooses the copy). `python3 tests/measure_idle.py` gives the
processor time at rest and while the toolbar is used, and the memory. Outside Arch, the Python packages of
`tools/test-requirements.txt` give the same Qt WebEngine from PyPI.

GitHub runs both on every pull request to `main` and every push to `main`
(`.github/workflows/tests.yml`, Ubuntu 24.04 with the packages of
`tools/test-requirements.txt`, the Chromium sandbox off as on the runner it
cannot start), then builds the Arch package with `makepkg`, runs the whole
suite again against the installed copy and keeps the package as the run's
`ike-browser-package` download.

Since 2026-11-24 the suite runs in parallel jobs on GitHub (both `tests.yml`
and `arch.yml`, four of each kind: the number `SHARDS` at the top of each
workflow). `tools/shard-tests.py` splits it by whole test files, balanced by
the durations recorded in `tools/test-timings.json` (a file not listed counts
as the `default`), always the same way for the same files. The job `tests`
(and `Arch Linux` in `arch.yml`) is the gate: it fails when a shard is
missing, failed or was cancelled, or when any test pytest collects did not run
exactly once across the shards, and it writes the run's junit files and "What
the tests verified" as before (a skipped test is still **not verified**). The
same split by hand, for one shard of four:

```bash
python3 tools/shard-tests.py collect --out /tmp/ids.txt
python3 tools/shard-tests.py plan --collected /tmp/ids.txt --shards 4 --shard 1
python3 tools/shard-tests.py run --kind source --shard 1 --shards 4 --out /tmp/shard-1
```

The recorded durations are refreshed from the junit files of a real run
(`python3 tools/shard-tests.py timings --junit junit.xml`); they only balance
the shards, the gate checks completeness whatever they say.

With `IKE_TEST_SHOTS=<folder>` some tests also save screenshots there, to be
checked by eye.

How a test works: `tests/conftest.py` starts `ike_boot.py` with
`IKE_TEST_HOOK=tests/harness.py`; the harness runs the test's `steps()`
generator inside the browser (each `yield` waits that many milliseconds with
the event loop running), saves what it recorded and closes the browser.
